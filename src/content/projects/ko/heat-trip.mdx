## 추천: LLM이 고르는 것과 Spring이 하는 것

<Figure
  src="/img/projects/heat-trip/recommend.svg"
  width={1000}
  height={938}
  alt="추천 한 번의 시퀀스(v2). 앱이 감정 값과 목표 키워드를 Spring에 보내면, Spring은 장소 목록 없이 감정 값과 키워드만 Python 추천 서버로 넘깁니다. 추천 서버는 95개 카테고리의 닫힌 목록으로 OpenAI에 묻고, 검증한 카테고리 라벨을 돌려줍니다. Spring은 라벨을 cat3 코드로 바꿔 MySQL에서 후보를 읽고 점수식으로 정렬해 앱에 돌려줍니다. 그림의 메모: pad·energy는 서버 DTO가 정수라 잘린 값이 단계 2와 10에 쓰입니다."
  caption="추천 한 번(v2, 스토어 1.0.0(3)) — 코드 줄은 034c3dc"
/>

**장소 목록은 프롬프트에 넣지 않습니다.** LLM은 95개 카테고리 이름 중에서 골라 두 그룹으로 묶어 돌려줍니다. 출력이 닫힌 목록이라, Spring은 메모리에 올린 카테고리 사전(`place_traits` 95행)으로 라벨을 cat3 코드로 바꿔 장소를 거릅니다. 대가로 사전에 없는 라벨은 버려지고, 매핑이 비면 장소 전체를 읽습니다(`findAll()`).

**순위는 LLM이 아니라 Spring의 점수식이 정합니다.** 최종 점수는 0.6×특성 일치 + 0.4×인기도입니다. 앱이 위치를 보내면 거리 점수를 0.2 비중으로 섞습니다. 상수는 손으로 정했고, 데이터로 검증한 기록은 없습니다.

**추천 서버가 LLM 출력의 형식을 검증하고 고칩니다.** 응답은 JSON 모드로 받아 Pydantic으로 검증하고, 실패하면 재요청, 위로 편지 보정, 정규화 순으로 처리합니다. 같은 입력은 5분 동안 캐시합니다. 캐시는 프로세스 메모리에 있어 인스턴스 하나를 전제로 합니다.

공모전 제출본(2025-09-19 제출)은 LLM이 없는 v1(2025-09-10, `b6fac1c`)입니다. v1은 전체 장소에 점수를 매기고, 감정 카테고리 18개(매핑 72개)로 묶어 보여 줬습니다. LLM을 쓰는 v2는 2025-10-18(`58da1b9`)에 들어와 스토어 1.0.0(3)에 실렸습니다. 두 판은 같은 `ScoringService`를 씁니다.

## 장소 데이터: 수집과 모델

  src="/img/projects/heat-trip/data.svg"

  alt="장소 데이터의 수집 순서와 개요 ERD. 수집은 관광공사 지역 목록 → 정제·절단 → places 배치 저장 순서이고, 그 뒤 Kakao 링크·좌표 보강과 CAT3 특성 스냅숏 → search_text(2026)로 갈라집니다. 아래에는 장소 카탈로그(places, place_traits, place_trait_snapshots, place_features, place_kakao_links), 감정 분류, 감정 피드백, 사용자·콘텐츠 묶음의 주요 표와, FK 실선과 FK 없는 논리 키 점선이 있습니다."
  caption="장소 데이터의 수집 순서와 주요 표 — 규모는 2026-10-01 로컬 DB"

- **수집.** 관광공사 지역 목록(`areaBasedList2`)을 받아 정제·절단(`Place.sanitizeAndTruncate`)한 뒤 배치로 저장합니다. 저장 뒤에는 두 작업이 갈라집니다. 하나는 Kakao Local로 링크와 좌표를 보강하는 작업이고(속성 플래그로 한 번 실행), 다른 하나는 CAT3 특성 스냅숏을 만들어 2026년부터 `search_text`를 채우는 작업입니다. 스케줄러는 주석 처리돼 있어 수동으로 돌리고, 실행 이력은 남기지 않습니다.
- **규모.** 장소는 50,098곳(이미지 있는 곳 38,871)입니다. 카테고리 사전은 95행, 감정 카테고리는 18개(매핑 72개)입니다.
- **키.** 장소 쪽 표는 FK 없이 `contentid`와 `cat3`로 잇습니다. 스키마는 Hibernate `ddl-auto`로 관리하고(마이그레이션 도구 없음), FULLTEXT 인덱스는 수동 SQL로 만듭니다.
- **무한 스크롤.** `(createdtime, contentid)` 커서를 Base64URL 토큰으로 주고받고, size+1개를 읽어 다음 페이지가 있는지 판단합니다. `contentid`를 둘째 키로 둬 같은 시각 행의 중복·누락을 막습니다. 목록 화면은 오프셋을 그대로 씁니다. 대가로 커서를 받칠 복합 인덱스 DDL이 레포에 없습니다.
- **미디어.** DB에는 S3 키만 저장하고, URL은 CloudFront 도메인과 키로 실행 때 만듭니다. 어디에 붙는 파일인지는 `ref_type/ref_id`로 적고(FK 아님), 삭제는 소프트 삭제입니다.

## 한계(고친다면)

| 한계 | 영향 | 고친다면 |
|---|---|---|
| 감정 값(PAD·에너지)을 서버 DTO가 정수로 받습니다 | 소수 입력이 대부분 0이 되어, 순위와 LLM 입력에 감정 특성이 거의 반영되지 않습니다. LLM에 온전히 가는 입력은 감정 칩, 목표 키워드, 사교성뿐입니다 | 실수 타입으로 바꾸고 앱–서버 계약 테스트를 둡니다 |
| 추천 서버 호출: 180초 타임아웃이 재시도마다 걸리고 4xx도 재시도하며, 톰캣 스레드가 `.block()`으로 기다리고 대체 응답이 없습니다 | 추천 서버나 OpenAI가 느리면 요청 스레드가 오래 묶이고 추천이 실패합니다 | 짧은 타임아웃, 4xx 재시도 제외, 규칙 기반(v1) 대체 응답을 둡니다 |
| 매핑이 비면 장소 전체를 읽고(`findAll()`), 커서를 받칠 복합 인덱스 DDL이 없으며, 스키마는 `ddl-auto`입니다 | 큰 표를 통째로 읽거나 정렬하는 쿼리가 생깁니다 | 빈 매핑은 빈 결과로 돌려주고, 인덱스와 스키마는 마이그레이션으로 관리합니다 |
| 테스트가 회귀를 잡지 못합니다(되돌려도 통과). 관측성 코드는 테스트·발송 기록이 없습니다 | 바꾼 뒤 안전한지 테스트로 알 수 없습니다 | 되돌리면 실패하는 테스트부터 씁니다 |
| 공개 앱 main이 컴파일되지 않습니다(스토어 빌드는 `5313bc7`, 복구 PR #9 열림) | 링크한 main으로는 출시 앱을 다시 빌드할 수 없습니다 | PR #9를 병합합니다 |
