저는 **팀 리드**로서 감정 기반 추천 로직, LLM 추천 서버 연동, 장소 검색·페이지네이션, 운영 관측성, 인증/보안 구조를 설계하고 구현했습니다. 아래는 "기능을 붙였다"가 아니라 **어떤 문제를 어떤 근거로 어떻게 풀었는지**를 정리한 것입니다.

## 시스템 아키텍처

Flutter 클라이언트가 REST로 Spring Boot 백엔드에 접근하고, 백엔드는 MySQL·S3/CloudFront·외부 API와 통신합니다. **LLM 추천은 Python 서버로 분리**하고 Port/Adapter로 연결했습니다.

데이터 모델은 장소와 장소 특성(`places`, `place_traits` 등), 사용자·북마크·컬렉션, 일정(`schedule`)과 일기(`journey`), 감정 피드백으로 나뉩니다. 일기는 일정에 연결하거나 따로 쓸 수 있고, 일정 상세와 Diary 탭에서 모아 봅니다.

## 핵심 기여 1 — 수만 건의 장소를 LLM에 넣지 않는다: LLM은 카테고리(cat3) 추천만

<Callout kind="problem">

LLM으로 장소를 추천하려 했지만, 가장 단순한 방법(사용자 입력 + 장소 데이터를 통째로 LLM에 전달)은 한국관광공사가 제공하는 **수만 개 장소 데이터**를 모두 입력 토큰으로 넣어야 해서 **컨텍스트 한계와 비용** 때문에 불가능하다고 판단했습니다.

</Callout>

<Callout kind="goal">

LLM의 자연어 추천 능력은 살리되, **현실적인 비용으로 실현 가능한** 구조를 만드는 것이 목표였습니다.

</Callout>

<Callout kind="solution">

LLM과 Spring의 책임을 나눴습니다. LLM은 **카테고리(`cat3`)** 만 추천하고, 실제 장소의 랭킹은 Spring 안에서 합니다.

- LLM이 추천한 category label을 Tour API의 내부 `cat3` 코드로 변환
- 실제 장소는 `cat3` 기반으로 필터링한 뒤, **감정 feature · 인기도 · 거리 점수**를 결합해 백엔드에서 최종 랭킹
- 프론트가 처음 받은 `cat3` 코드를 `cat3Filter`로 넘겨 다시 요청하면 **LLM 단계를 건너뛰고 랭킹만 수행**

</Callout>

<Callout kind="result">

수만 건의 장소를 LLM 입력으로 넣지 않고도 감정 기반 맞춤 추천을 제공할 수 있게 됐습니다.

**한계:** LLM 호출이 실패하면 대체 응답이 없고, 긴 타임아웃이 재시도마다 적용됩니다. 다음 단계는 타임아웃 단축과 fallback(규칙 기반 추천)으로 요청 스레드가 묶이지 않게 하는 것입니다. 이후 Redis 캐싱(동일 입력 LLM 출력 캐싱), VectorDB 기반 RAG 전환도 개선 방향으로 두고 있습니다.

</Callout>

## 핵심 기여 2 — 사용 패턴이 다른 두 페이지네이션 분리

<Callout kind="problem">

장소 목록은 **일반 페이지 조회**와 **모바일 무한 스크롤**이라는 서로 다른 사용 패턴을 가졌습니다. Offset 방식만 쓰면 무한 스크롤에서 데이터가 많아질수록 성능 저하와 중복/누락 문제가 생길 수 있었습니다.

</Callout>

<Figure
  src="/img/projects/heat-trip/flow-explore.webp"
  width={1600}
  height={718}
  alt="관광지 탐색(Explore) 흐름도: 테마 선택 또는 검색 → 관광지 목록 → 상세 페이지 → 북마크 저장 → 프로필의 북마크 탭에서 확인하는 앱 화면 5장"
  caption="관광지 탐색(Explore) 흐름도 — 공모전 기능설명서 중(팀 공동 작성)"
/>

<Callout kind="solution">

전략을 분리했습니다. **일반 목록은 Offset Pagination**, **무한 스크롤은 `createdtime` + `contentid`를 복합 정렬 키로 쓰는 Cursor Pagination**으로 구현했습니다. cursor는 Base64 토큰으로 인코딩하고, `size + 1`개를 조회해 다음 페이지 존재 여부를 판단했습니다.

</Callout>

<Callout kind="result">

무한 스크롤에서 안정적인 다음 페이지 조회가 가능해졌고, 동일 `createdtime` 데이터가 있어도 `contentid` 보조 정렬로 **순서가 고정**되어 중복/누락을 막았습니다.

</Callout>

## 핵심 기여 3 (개인 리팩토링) — 실행 계획으로 병목을 찾고 장소 검색 구조를 바꿈

<Callout kind="problem">

장소 약 4.9만 건에서 `q=카페` 같은 텍스트 검색이 `LOWER(col) LIKE '%카페%'` 4개와 카테고리명을 찾는 `EXISTS` 상관 서브쿼리로 되어 있었습니다.

`EXPLAIN ANALYZE`로 보니 진짜 병목은 목록이 아니라 **count 쿼리**였습니다. 전체 테이블 스캔에 서브쿼리가 약 4.9만 번 반복돼 **약 755ms**가 걸렸습니다. 앞쪽 와일드카드와 `LOWER()` 때문에 B-Tree 인덱스를 추가해도 텍스트 검색 경로는 풀리지 않았습니다.

</Callout>

<Callout kind="solution">

장소명·카테고리·카테고리명을 `search_text` 컬럼으로 **반정규화**하고, `FULLTEXT INDEX … WITH PARSER ngram` + `MATCH … AGAINST`로 바꿨습니다.

</Callout>

<Callout kind="result">

변경 후 목록은 Fulltext 인덱스에서 후보(약 3,468건)를 바로 찾아 전체 **약 4.9ms**, count도 전체 스캔과 서브쿼리 반복이 사라졌습니다.

주의한 점: 755ms(변경 전 count)와 4.9ms(변경 후 목록)는 서로 다른 쿼리의 수치입니다. 변경 전 `LIMIT 20` 목록 쿼리만 떼어 비교하면 옛 방식이 더 빨라 보일 수 있어, API가 목록과 count를 함께 처리한다는 점을 기준으로 숫자 한 줄이 아니라 검색 경로 전체로 판단했습니다. 마이그레이션 절차와 SQL 로그 테스트, 전후 실행 계획을 [문서 8편](https://github.com/sanghyunbang/Heat_Trip_Spring_Boot_BE/tree/main/docs/database/sql-query-optimization-search)으로 남겼습니다.

**한계:** FULLTEXT 검색은 `LIKE`와 결과가 완전히 같지 않습니다(한 글자·특수문자 검색어). 성능과 검색 의미 사이의 트레이드오프로 보고, 짧은 검색어·조건 조합별 결과 비교를 마무리하는 것이 다음 단계입니다.

</Callout>

## 핵심 기여 4 (개인 리팩토링) — 품질·운영 관측성 기반 구축

<Callout kind="problem">

외부 API·LLM 서버·이미지 업로드·인증 등 장애 가능성이 많았고, 추천·인증 흐름은 변경 시 회귀가 쉬운 핵심이었습니다. **개발 중엔 빠른 발견, 운영 중엔 원인 추적**이 필요했습니다.

</Callout>

<Callout kind="solution">

- 추천 orchestration, LLM 응답 DTO 역직렬화, 인증 서비스에 **단위 테스트** 작성
- **JaCoCo** 커버리지 리포트(빌드 시 생성) · **Qodana** 정적 분석(GitHub Actions)
- Controller 처리 시간·예외를 **AOP**로 수집, 에러는 **fingerprint 기반 중복 억제** 후 **Slack** 알림
- 민감정보 마스킹 + `correlation id`로 로그 추적성과 보안 동시 고려

</Callout>

<Callout kind="result">

핵심 흐름(추천·LLM DTO·인증)의 회귀를 테스트로 방어하고, 운영 중 에러를 Slack 알림과 `correlation id`로 더 빠르게 인지·추적할 기반을 마련했습니다. Qodana/JaCoCo는 아직 가시화 단계지만, 핵심 패키지 중심으로 품질 게이트를 강화할 출발점이 되었습니다.

</Callout>
