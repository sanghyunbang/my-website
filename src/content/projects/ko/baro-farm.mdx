## 시스템 구성

구성도는 [위 커버 그림](#cover)입니다(금색 = 맡은 부분, 회색 = 팀원, 점선 = 폴링·비동기).

- 인가 판단은 OPA(PDP)가 하고, 게이트웨이는 그 결과를 집행(PEP)만 합니다.
- 상태 변경은 auth-service → Kafka(`opa-hotlist-events`) → opa-bundle → OPA 번들 폴링으로 인가 데이터에 반영됩니다. 같은 토픽을 seller-service가 소비해 판매자 상태를 맞춥니다.
- Spring Security는 auth-service에만 있습니다. 나머지 서비스는 게이트웨이가 쓴 `X-User-*` 헤더를 그대로 사용자 식별에 씁니다. 그래서 게이트웨이 필터가 신뢰 경계입니다.

## 요청 하나가 지나가는 길

  alt="요청 하나의 인가 경로. 브라우저가 쿠키를 실어 보낸 요청은 API Gateway의 라우트 필터인 Authentication 필터와 OpaAuthorization 필터를 차례로 지나고, 게이트웨이에는 기본 필터(RateLimiter·Retry·CircuitBreaker)도 걸려 있습니다(합친 실행 순서는 확인하지 않음). 인가 필터는 OPA에 request·subject·route.service를 보내 결과를 받고, true이면 하류 서비스로 라우팅합니다. 토큰 검증 실패는 401, 정책 결과 false나 결과 없음은 403, OPA 오류·2초 초과·서킷 열림·벌크헤드 포화는 503입니다. 토큰이 없으면 들어온 X-User-* 헤더를 그대로 둔 채 통과합니다."
  caption="게이트웨이 78eaa987 · 403은 정책이 기본 거부였던 01-22~01-26 기준"
/>

로그인하면 auth-service가 access·refresh JWT를 HttpOnly·Secure·SameSite=Strict 쿠키로만 내려 줍니다. access JWT는 HS256으로 서명하고 sub(이메일), uid, 역할, user_status, seller_status, flags를 담습니다. 유효기간은 access 7일, refresh 14일입니다.

**판단과 집행을 나눴습니다.** 경로·역할 규칙을 게이트웨이 코드 배포 없이 정책과 데이터로 바꾸기 위해서입니다. 대가는 요청마다 붙는 OPA 호출 한 번(2초 제한)입니다.

**규칙은 서비스·역할별 데이터 묶음입니다.** 게이트웨이는 질의에 `route.service`를 넣고, OPA는 그 서비스의 묶음만 평가합니다. 메서드 색인(`index.method`)으로 후보 규칙을 한 번 더 줄입니다. `data[service]` 가변 조회가 정책 패키지 자신을 가리켜 생긴 순환 오류는 명시적 데이터 루트로 풀었습니다. 대가로 서비스가 늘 때마다 rego를 고쳐야 하고, 라우트 id 규칙에 서비스 이름이 묶입니다. 규칙 한 건은 아래와 같습니다(`baro-cloud/opa/policy/data/buyer/seller.json` @`78eaa987`에서 발췌, 들여쓰기만 정리).

```json
"buyer:products-create": {
  "name": "buyer:products-create",
  "path": "^(/buyer-service)?/api/v1/products$",
  "methods": ["POST"],
  "roles": ["SELLER", "ADMIN"],
  "deny_flags": ["PRODUCT_PUBLISH_BLOCKED"]
}
```

**OPA가 실패하면 닫습니다.** OPA 오류, 2초 초과, 서킷 열림, 벌크헤드 포화는 모두 503입니다. 가용성을 내준 선택이고, fail-open 대안은 설계 문서에 남겼습니다.

## 상태가 바뀌면

**토큰에는 굵은 권한만 두고, 바로 반영할 상태는 hotlist로 보냈습니다.** 이미 발급된 JWT는 만료 전까지 옛 역할을 담고 있습니다(access 7일). 그래서 사용자 정지·차단·탈퇴와 판매자 승인·거절·정지는 hotlist 데이터로 OPA에 보냅니다. 토큰의 `seller_status`는 항상 UNKNOWN이라 판매자 상태는 hotlist로만 알 수 있습니다. 대가는 OPA 번들 폴링 주기(10–60초, 설정값)만큼의 지연입니다.

**번들은 OPA가 가져가는(pull) 방식이고, 이벤트마다 전체를 다시 만듭니다.** opa-bundle은 기동할 때 data.json에서 hotlist를 복구합니다. OPA는 마지막 정상 번들을 계속 씁니다. 대가로 메모리 저장소라 인스턴스는 하나만 둘 수 있고, 번들 파일은 임시 파일 없이 덮어씁니다.

**Kafka 키는 subjectId입니다.** 사용자별 순서를 지키기 위해서입니다. 번들 서비스는 eventId로 중복을 거릅니다(최근 10,000개).

판매자 hotlist가 게이트웨이 인가에 쓰인 것은 승인 규칙이 정책에 있던 01-22~01-26뿐입니다. 발표 커밋의 정책은 판매자 hotlist를 읽지 않습니다. 그 기간에도 상품 서비스는 토큰의 역할 헤더로 판매자를 다시 검사했습니다.

### 이벤트를 내보내는 세 가지 방식

| 경로 | 방식 | 지켜지는 것 | 빈틈 |
|---|---|---|---|
| 사용자·판매자 상태 → `opa-hotlist-events` (발표 시점) | 트랜잭션 안에서 `KafkaTemplate.send`, 결과를 기다리지 않음. 키 = subjectId | 사용자별 순서. 소비자가 eventId로 중복을 거름 | 롤백돼도 이벤트가 나갈 수 있음. 브로커 장애면 로그만 남고 사라짐 |
| 회원탈퇴 → `user-events` (발표 시점, 01-20) | outbox: 같은 트랜잭션에 이벤트 행 적재 → 1초 스케줄러 → `send().get(5s)` → PUBLISHED, 5회 실패면 FAILED | 탈퇴가 커밋되면 이벤트 행도 반드시 있음 | 소비자가 아직 없음. 여러 인스턴스용 잠금·백오프 없음. 같은 탈퇴의 hotlist 전파는 outbox가 아니라 커밋 전 직접 전송 |
| 판매자 승인 (2026-03 개인 브랜치, 미병합) | `afterCommit` 동기화 → `@Async("opaEventExecutor")` → Kafka | 승인 커밋과 응답이 브로커에 막히지 않음. 롤백된 승인은 나가지 않음 | 전송이 실패하면 다음 토큰 갱신(최악 7일)까지 반영되지 않음. 관리자 경로만 해당(`grantSeller`는 여전히 트랜잭션 안 동기). 테스트 없음 |

즉시성이 필요한 인가 데이터와 유실되면 안 되는 탈퇴 이벤트를 다르게 다뤘지만, 발표 시점의 hotlist 경로는 유실도, 롤백된 변경의 이벤트(유령 이벤트)도 막지 못했습니다. 3월 브랜치의 커밋 뒤 전송은 그중 유령 이벤트 쪽만 막습니다.

## 발표 이후

2026-02에는 팀 레포 main에서 모듈을 정리했습니다(PR #92·#94·#102). auth와 seller를 `baro-user`로 합치고, `baro-cloud/*`를 최상위 모듈로 올리고, 알림을 `baro-notification`으로 나눴습니다. 게이트웨이에서는 Eureka 클라이언트를 뺐습니다. **이 과정에서 라우트의 OPA 인가 필터가 빠졌습니다(본인 커밋 `3f98d694`).** 지금 main의 prod 프로필 라우트는 K8s 서비스 DNS 주소를 씁니다.

2026-03에는 개인 브랜치(미병합)에서 판매자 관리자 API를 도메인으로 분리했습니다. 승인 뒤 OPA 전파는 커밋 뒤 별도 실행기로 옮겼고, 그 결정을 [ADR(커밋 `59f643a6`)](https://github.com/dogs-team/baro-farm-be/blob/59f643a6de76442c4e14fb97b8221dab99d7bfd0/docs/ADR_SELLER_APPROVAL_AFTER_COMMIT.md)로 남겼습니다. 이 변경은 관리자 경로에만 해당하고 테스트가 없습니다. 브랜치의 테스트는 컴파일되지 않습니다.
