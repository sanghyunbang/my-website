KDT 풀스택 캠프 졸업 프로젝트로 4인 팀이 약 한 달(2025.06.02–07.03, 팀 발표 자료 기준) 동안 만든 등산 커뮤니티입니다. 맡은 범위는 지도(산 검색, 산악 예보, 등산로 표시), 큐레이션 글, 소셜 로그인과 S3 업로드이고, 각 기능의 백엔드와 프론트를 함께 작업했습니다. 두 레포의 초기 구조(Spring Boot 프로젝트, React 앱 골격, 라우팅, 상태 관리, 개발 프록시)를 구성했습니다.

아래는 기능별로 내린 결정과, 이번에 코드를 다시 읽으며 확인한 한계를 정리한 것입니다.

## 시스템 구성

React(Tailwind CSS) 웹이 Spring Boot 서버를 호출합니다. 서버는 Spring Security와 JWT로 인증하고, 게시판 데이터는 MyBatis로 MySQL에, 큐레이션 글의 경로 구간은 MongoDB에, 날씨 예보는 Redis에 둡니다. 미디어는 S3에 올리고 CloudFront 주소로 내려줍니다. 외부 데이터는 기상청 API허브(산악 예보), VWorld(등산로), 카카오 지도 SDK를 씁니다.

## 핵심 기여 1 — 지도와 산악 예보: 외부 API 호출을 화면 요청에서 분리

<Callout kind="problem">

지도에서 산을 고를 때마다 기상청 API를 호출하면 화면 응답이 외부 API 속도에 묶이고, 호출 한도도 빠르게 소모됩니다. 예보는 하루에 몇 번만 바뀌는 데이터라 요청 시점에 받아 올 필요가 없었습니다.

</Callout>

<Callout kind="solution">

- 기상청 산악 예보 지점 153곳을 JSON으로 두고 서버 시작 시 메모리에 올렸습니다. 산 검색은 이 목록에서 처리합니다.
- 예보는 WebClient와 Reactor로 일괄 수집합니다. 산 목록을 5개씩 묶어 묶음 단위로 차례로 처리하고, 묶음 안에서는 요청 시작을 500ms 간격으로 띄웠습니다. 결과는 산마다 Redis에 12시간 TTL로 저장합니다.
- 지도 화면의 예보 API는 Redis만 읽습니다.
- 등산로는 검색한 산 좌표 주변의 VWorld 등산로 데이터를 받아 카카오 지도 위에 난이도별 색으로 그립니다.

</Callout>

화면 요청 경로에서 외부 API 호출을 뺐습니다.

**한계 — 자동 갱신 트리거:** 전체를 한 번 갱신하면 기상청 API를 153번 호출합니다. 호출 한도 때문에 최종 코드에서는 스케줄 실행과 서버 시작 시 실행을 모두 꺼 두었고, 그래서 최종 코드에는 예보 캐시를 채우는 실행 경로가 없습니다.

**한계 — 재시도:** 코드를 다시 읽어 보니, 호출 메서드가 오류를 빈 목록으로 바꾸기 때문에 뒤에 붙인 백오프 재시도(최대 2회)가 실행되지 않습니다. 그 결과 실패한 산에는 빈 값이 12시간 동안 캐시됩니다. 오류 변환을 재시도 뒤로 옮기고, 실패하면 이전 값을 유지하고, 호출마다 응답 타임아웃을 두는 것이 고칠 방향입니다.

</Callout>

## 핵심 기여 2 — 큐레이션 글: 경로 구간은 MongoDB, 글은 MySQL

<Callout kind="problem">

큐레이션 글은 등산 경로를 지점과 길 구간으로 나눠 기록하는 글입니다. 지도에 마커를 N개 찍으면 지점과 길이 번갈아 2N−1개 구간이 되고, 구간마다 좌표, 난이도, 주의 사항, 편의시설 목록, 사진이 붙습니다. 글마다 구간 수와 좌표 수가 달라 일반 게시판 테이블 구조에 그대로 넣기 어려웠습니다. 처음에는 MySQL에 큐레이션 상세 테이블을 두었다가, 구간 구조로 바꾸면서 정리했습니다.

</Callout>

<Callout kind="solution">

- 글의 공통 정보(작성자, 게시판, 제목, 대표 좌표)는 MySQL `posts`에, 구간은 MongoDB 문서(GeoJSON 좌표, 설명, 사진 URL)로 저장하고 `postId`로 연결했습니다.
- 글 상세와 게시판 목록에서는 글 유형이 큐레이션이면 MongoDB에서 구간을 붙여 응답합니다. 큐레이션 검색은 MongoDB에서 본문이 맞는 구간을 찾은 뒤 해당 글을 MySQL에서 조회합니다.
- 글쓰기 화면에서는 지도를 클릭할 때마다 마커와 선분을 그리고, 상세 화면은 저장된 좌표로 경로를 다시 그립니다.
- 지도 페이지에서 산을 검색하면 그 중심 반경 3km 안에 있는 큐레이션 글 작성자의 프로필을 지도에 띄우고, 누르면 글로 이동합니다.

</Callout>

경로와 구간별 설명, 사진이 붙은 글을 지도와 함께 보여 줄 수 있게 됐습니다.

**한계 — 저장소 간 일관성:** 글 저장은 MySQL → S3 → MongoDB 순서로 이뤄지는데, 이를 묶는 장치가 없습니다. 중간에 실패하면 구간 없는 글이나 참조되지 않는 파일이 남을 수 있습니다. 서버의 한 요청에서 순서를 관리하고, 글을 임시 상태로 만들었다가 구간 저장이 끝난 뒤 공개하는 방식이 고칠 방향입니다.

**한계 — 반경 조회:** 반경 3km 조회는 문자열로 저장한 대표 좌표를 행마다 잘라 거리를 계산하므로 인덱스를 쓰지 못합니다. 좌표 범위 조건을 먼저 걸거나 공간 인덱스를 쓰는 것이 다음 단계입니다.

</Callout>

## 핵심 기여 3 — 소셜 로그인(OAuth2 + JWT)과 S3 업로드

<Callout kind="solution">

- Spring Security OAuth2 Client로 네이버·구글 로그인을 처리합니다. 공급자마다 다른 사용자 정보 응답을 한 인터페이스로 맞추고, 이메일로 기존 사용자를 찾거나 새로 만듭니다(닉네임은 자동 생성).
- 로그인에 성공하면 JWT를 HttpOnly 쿠키로 내려주고, 요청마다 필터가 헤더 또는 쿠키의 토큰을 검증해 인증 정보를 만듭니다. 프론트는 새로고침할 때 서버에 로그인 상태를 물어 Redux 상태를 복구합니다.
- 게시글과 구간의 사진·영상은 S3에 UUID를 붙인 키로 올리고, CloudFront 주소를 돌려줍니다.

</Callout>

<Callout kind="result">

**한계:** 소셜 로그인 경로의 액세스 토큰 만료 시간이 약 20.8일로 설정돼 있고(주석은 30분), 리프레시 토큰은 발급만 하고 갱신 경로가 없습니다. CSRF 보호를 끈 채 쿠키로 인증하고, 업로드 파일의 형식과 크기를 코드에서 검사하지 않습니다. 짧은 액세스 토큰과 서버에 저장하는 리프레시 토큰(사용할 때마다 교체), 쿠키 SameSite 지정, 업로드 검증이 고칠 방향입니다.

</Callout>

## 팀 작업과 일정

게시판 화면, 서브 커뮤니티와 피드, 굿즈·장바구니·주문·결제, 일반 로그인·회원가입은 주로 다른 팀원이 맡았습니다. 커버 이미지의 커뮤니티 화면도 주로 팀원이 만든 기능입니다. 일정은 기획·역할 분담(6/2–6/4), 설계·개발(6/4–6/25), 디자인 통일·테스트(6/25–6/30), 최종 발표(7/3) 순서로 진행했습니다.
