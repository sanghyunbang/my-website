## Contribution 1 — Per-room chat sequence: concurrent messages getting the same number

<Callout kind="problem">

Each chat room numbers its messages 1, 2, 3… Reading the room and writing +1 lets two requests read the same value, so they hit the per-room sequence unique constraint.

</Callout>

<Callout kind="solution">

Reading with `SELECT … FOR UPDATE` and writing +1 also serializes the requests. But it has to read the row again, and it risks reading a stale value from the JPA first-level cache. So I bundled the increment and "get my number" with `LAST_INSERT_ID(expr)`.

```sql
UPDATE chat_room SET last_seq = LAST_INSERT_ID(last_seq + 1) WHERE id = ?;
SELECT CAST(LAST_INSERT_ID() AS SIGNED);   -- same transaction, before the INSERT
```

What serializes the requests is the UPDATE's row lock. `LAST_INSERT_ID(expr)` leaves the incremented value in my session, so I get my number without reading the row again.

When a mobile client resends the same message, a unique constraint per room and sender — `(room_id, sender_user_id, client_msg_id)` — stops the duplicate. On a constraint violation, the server returns 200 only if a row with that key actually exists.

</Callout>

<Callout kind="result">

A test on real MySQL (Testcontainers) pins that when 20 threads send to the same room at once, sequence numbers 1–20 each come out exactly once. The default connection pool is 10, so at most 10 transactions actually run concurrently.

Resend idempotency is pinned by three cases: same ID duplicated / same key from another member / no key.

</Callout>

## Contribution 2 — First production deploy: a passing test was agreeing with a broken config

<Callout kind="problem">

On the first production boot on 2026-09-17, every container came up but ports 80 and 443 did not respond. Caddy had exited right after start on a config parse error (two path matchers listed on one `handle`).

The test guarding the config checked strings in the Caddyfile, so it passed the broken config because "the string is there."

</Callout>

<Callout kind="solution">

I replaced it with a test that starts the same Caddy image as production via Testcontainers and actually runs `caddy validate`.

Mount paths and health checks were reinforced with static checks that read the compose files, and the docs site is checked by actually rendering it.

</Callout>

<Callout kind="result">

That same week I learned that even an execution test gives a false green if it runs differently from production (by copying files in), so I changed the bar from "does it execute" to "does it run under the same conditions as production."

</Callout>

## Contribution 3 — Module boundaries and test structure

A modular monolith on Spring Modulith (22 top-level modules). The Modulith checks run in tests; only the annotation API is a runtime dependency.

- **Boundary-violation ratchet** — I introduced boundary checks after the fact, cut violations from **620 to 107**, and locked them with a ratchet so the test fails if they grow.
- **Cycles and cross-module references** — zero dependency cycles between modules (`ModuleCycleTest`). Foreign keys and joins that cross modules are held at a baseline by tests so they cannot grow.
- **Full test run** — 1,994 backend tests, 0 failures (2026-09-30, GitHub main, about 18 minutes).
- **Production setup** — production is a single EC2 instance provisioned with Terraform, with Caddy as the only entry point handling TLS. Prometheus and Grafana exist only in staging and locally.
- **Decision records** — 23 (18 of them compare alternatives).

## Limitations & next steps

| Current state | Next |
|---|---|
| Early after launch, one server, no load test yet. The chat sequence timer (`chat.seq.assign`) is already recorded, but histograms are off, so p99 can't be computed | Turn on histograms and measure response time (p99) and sequence-lock waits under real traffic. No cache or message queue until a need is measured |
| Deploys recreate containers, causing a short outage. The container start command is `sh -c` without exec, so the stop signal (SIGTERM) may not reach the JVM. In an experiment with the same base image PID 1 was the shell; not yet checked with the actual app image | Measure and fix the signal path first (exec form). Then tune the stop grace period, move to blue/green deploys and measure the error rate during a deploy |
| On logout and account deletion, device push-token cleanup runs on an async queue after commit. It can be lost if the queue is full or the process stops for a deploy | Move cleanup that must not be lost into the transaction, and pin it with a test that injects queue saturation |
| The chat read-marking path locks in the opposite order to the documented lock order, so it can deadlock when it coincides with a send in the same room (reproduced in code review; a reproduction test is still to be written). It currently responds with 500 | Reproduction test → unify the lock order → confirm the 20-thread test stays green → update the lock-order comments |
| Production has no metrics collector (Prometheus/Grafana are staging and local only) | Add production collection and build a chat-metrics panel |
| 107 module-boundary violations remain | Keep reducing them with the ratchet |
