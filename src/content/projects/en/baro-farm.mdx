## Problem

While owning the member/auth service, the Gateway and OPA authorization in an MSA environment, **intermittent 403 (Forbidden)** errors appeared during development. They were hard to reproduce, and viewing them as a mere gateway response error led nowhere. They clustered right after user-state changes such as seller approval.

## Cause — a state mismatch, not the surface

I chose not to treat this as a gateway response error, and hypothesized a **structural problem: the permission info carried in the JWT diverging from the latest user state**.

Permissions are issued inside the JWT, but when approval, suspension or withdrawal changes the user's state, already-issued tokens stay the same. Until the token was refreshed, the gateway decided with the old permissions, producing 403s during that **lag window**.

## Solution — letting state changes flow through

- Publish state changes from approval, suspension and withdrawal as **Kafka hotlist events**
- The opa-bundle service consumes them and **rebuilds the OPA bundle** (policy + data)
- OPA pulls the bundle periodically, so the gateway's authorization queries see the latest state

The bundle endpoint only accepts private-network (private IP/CIDR) clients, with an optional internal-token check that can be enabled by config.

I **designed and implemented this path to cut the lag between permission info and user state to within the OPA polling interval (10–60s)**, and the policy rule ran from 2026-01-22 to 01-25. It was never meant to eliminate the lag.

On main, however, this blocking does not run. On 2026-01-26, the day before the project ended, the policy default was switched to allow (`default allow := true`), and main still has it; the gateway routes on main also have no OPA filter attached. Even while the rule ran, the downstream product service checked seller status from the role header in the token, so 403s right after approval remained on that path. The accurate summary is "diagnosed the cause and designed and implemented a path to shrink the lag, but it is inactive on main," not "reduced the lag."

## Result

I gained the perspective of seeing a failure not as a visible symptom (403) but as a **data-consistency and event-propagation** problem. Auth/authorization isn't a single service — it works only when the state across multiple components stays consistent. I also learned that unless a policy is pinned by tests that actually run, a one-line change right before a deadline (default allow) can switch the whole design off.

## Gateway filter order and token storage

The designed filter order is: the Gateway's global filters (Rate Limit → Retry → Circuit Breaker → Timeout), then the authentication filter enriches the request headers and the OPA authorization filter gets an allow/deny before the request goes downstream (per the team presentation). The routes on main currently have no OPA authorization filter attached. Auth tokens are issued as HttpOnly cookies instead of localStorage so scripts can't read them, and the cookies carry `SameSite=Strict` so they are not sent on requests started from other sites.

## How seller approval and member withdrawal are delivered

I implemented the withdrawal outbox on main during the project (2026.01). Separating seller-approval propagation was solo refactoring after the project (2026.02–03), and I recorded that decision in an [ADR (link pinned to commit `59f643a6`)](https://github.com/dogs-team/baro-farm-be/blob/59f643a6de76442c4e14fb97b8221dab99d7bfd0/docs/ADR_SELLER_APPROVAL_AFTER_COMMIT.md) (the ADR covers seller approval only). The seller-approval change and the ADR live on the `test/issue-103-integration-test-payment` branch and are not merged into main.

- **Problem** — Seller approval handled "state change → permission change → Kafka publish" as a single unit, so if the broker paused or slowed briefly, the approval itself failed or the request timed out.
- **Seller approval (solo refactoring)** — On the admin approval path, the approval is committed first and OPA propagation is sent on a separate thread after commit. The other entry point (`grantSeller`) still publishes synchronously inside the transaction, and this change has no tests. If propagation is lost, the next token refresh re-reads the role from the database, so I accepted eventual consistency — but tokens live for 7 days, so the worst-case recovery time is also 7 days.
- **Member withdrawal (implemented during the project)** — I designed it as an event other services would be told about (no service consumes it yet; design only), and a lost event cannot be rebuilt, so inside the withdrawal transaction, together with anonymizing personal data and deleting credentials/tokens, the event is written to an outbox table; a scheduler publishes it and updates its status based on the result. After 5 failures it is marked FAILED.
