## System architecture

A Flutter client talks to the Spring Boot backend over REST, and the backend communicates with MySQL, S3/CloudFront and external APIs. The **LLM recommendation is split into a Python server** and connected via a Port/Adapter.

<ArchitectureHeatTrip />

The data model splits into places and place traits (`places`, `place_traits`, etc.), users · bookmarks · collections, schedules (`schedule`) and diary entries (`journey`), and emotion feedback. A diary entry can be attached to a schedule or written on its own, and entries are gathered in the schedule detail and the Diary tab.

## Contribution 1 — Not feeding tens of thousands of places to the LLM: it recommends categories (cat3) only

<Callout kind="problem">

I wanted to recommend places with an LLM, but the simplest approach (sending user input + all place data straight to the LLM) would require feeding the **tens of thousands of places** from the Korea Tourism API as input tokens — impossible due to **context limits and cost**.

</Callout>

<Callout kind="goal">

Keep the LLM's natural-language recommendation ability, but build a structure that is **feasible at a realistic cost**.

</Callout>

<Callout kind="solution">

I split responsibilities between the LLM and Spring. The LLM recommends only a **category (`cat3`)**, and ranking of actual places happens inside Spring.

- Convert the LLM's category label into the Tour API's internal `cat3` code
- Filter actual places by `cat3`, then rank on the backend by combining **emotion features · popularity · distance scores**
- When a request sends back the initial `cat3` code as `cat3Filter`, **the LLM step is skipped and only ranking runs** (server path only; the current app does not send it)

</Callout>

<Callout kind="result">

This gave a recommendation structure that does not feed tens of thousands of places into the LLM.

**Limitation — emotion-input contract mismatch:** the app sends emotion values (PAD and energy) as floats from -1 to 1, but the server DTOs take integers, so most values truncate to 0 (e.g. 0.7 / -0.4 / 1.0 / 0.9 → 0 / 0 / 1 / 0). Right now emotion features barely affect the ranking. The planned fix is to write a contract test first and then align the types on both sides.

**Limitation — LLM failure handling:** there is no fallback response when the LLM call fails, and a long timeout applies to every retry. The next step is to shorten the timeout and add a rule-based fallback so request threads aren't held up. Redis caching (same-input LLM output) and a VectorDB-based RAG approach are further improvements I'm considering.

</Callout>

## Contribution 2 — Splitting two pagination patterns

<Callout kind="problem">

The place list had two different usage patterns: **regular page browsing** and **mobile infinite scroll**. Using offset alone would degrade performance and cause duplicate/missing rows in infinite scroll as data grows.

</Callout>

<Figure
  src="/img/projects/heat-trip/flow-explore.webp"
  width={1600}
  height={718}
  alt="Place exploration (Explore) flow, five app screens in Korean: pick a theme or search → place list → detail page → save a bookmark → check it in the profile's bookmark tab"
  caption="Place exploration (Explore) flow — from the competition feature document (team-authored, Korean)"
/>

<Callout kind="solution">

I split the strategy. **Regular lists use Offset Pagination**, while **infinite scroll uses Cursor Pagination with `createdtime` + `contentid` as a composite sort key**. The cursor is Base64-encoded, and I fetch `size + 1` rows to decide whether a next page exists.

</Callout>

<Callout kind="result">

Infinite scroll gets stable next-page fetching, and even with identical `createdtime` values, the `contentid` tiebreaker **fixes the order**, preventing duplicates/omissions.

</Callout>

## Contribution 3 (solo refactoring) — Finding the bottleneck with execution plans and restructuring place search

<Callout kind="problem">

Over roughly 49k places (estimated), a text search such as `q=카페` ("cafe") was implemented as four `LOWER(col) LIKE '%카페%'` conditions plus an `EXISTS` correlated subquery to match category names.

`EXPLAIN ANALYZE` showed the real bottleneck was not the list query but the **count query**: per the documented execution plan, a full table scan with the subquery repeated about 49k times, taking **about 755ms**. Because of the leading wildcard and `LOWER()`, adding a B-Tree index could not fix the text-search path.

</Callout>

<Callout kind="solution">

I **denormalized** place name, category and category name into a `search_text` column and switched to `FULLTEXT INDEX … WITH PARSER ngram` + `MATCH … AGAINST`.

</Callout>

<Callout kind="result">

After the change, the list query finds candidates (about 3,468 rows) directly from the fulltext index, **about 4.9ms** end to end (a single measurement for '카페', including the `contentid` sort), and per the documented execution plan the count query no longer does a full scan or repeats the subquery. The count SQL in the code has a LEFT JOIN, though, so I still need to re-measure to confirm the documented plan is for the same SQL.

Caveat: 755ms (count, before) and 4.9ms (list, after) measure different queries. Comparing only the old `LIMIT 20` list query in isolation can make the old approach look faster, so since the API runs both list and count, I judged by the whole search path rather than a single number. I documented the migration steps and before/after execution plans in [8 documents](https://github.com/sanghyunbang/Heat_Trip_Spring_Boot_BE/tree/main/docs/database/sql-query-optimization-search) (Korean). The search API test currently checks only the response code (200), so it still passes if the code is reverted to `LIKE`; I plan to replace it with a test that checks the FULLTEXT path on real MySQL.

**Limitation:** FULLTEXT results are not identical to `LIKE` (single-character and special-character queries). I treat this as a trade-off between performance and search semantics; finishing result comparisons for short queries and condition combinations is the next step.

</Callout>

## Contribution 4 (solo refactoring) — Adding unit tests and observability code

<Callout kind="problem">

External APIs, the LLM server, image uploads and auth were all failure-prone, and the recommendation/auth flows were core paths prone to regression on change. I needed a way to **catch problems early and trace the cause when an error happens**.

</Callout>

<Callout kind="solution">

- **Unit tests** for recommendation orchestration, LLM-response DTO deserialization, and the auth service
- **JaCoCo** coverage reports (generated in the build) · **Qodana** static analysis (GitHub Actions)
- Collected controller latency & exceptions via **AOP**; errors are **deduplicated by fingerprint** then sent to **Slack**
- Sensitive-data masking + a `correlation id` for both log traceability and security

</Callout>

<Callout kind="result">

I wrote unit tests for recommendation orchestration, the LLM-response DTO and the auth service, and added observability code (AOP collection, fingerprint-deduplicated Slack alerts, `correlation id`). Qodana/JaCoCo are still at the visibility stage.

**Limitation:** some tests stay green even when the change they cover is reverted (e.g. the LLM-response DTO deserialization test and the search adapter test), so they are not real regression guards yet; I plan to replace them with tests that fail on revert. The observability code has no tests yet and no record of an alert actually being sent, and it has design flaws to fix — the OpenAI and Slack calls run synchronously on the request path, and 4xx responses also trigger alerts.

</Callout>
