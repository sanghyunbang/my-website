As **team lead**, I designed and built the emotion-based recommendation logic, the LLM recommender integration, place search & pagination, operational observability, and the auth/security structure. Below is not "I added features" but **what problem I solved, on what basis, and how**.

## System architecture

A Flutter client talks to the Spring Boot backend over REST, and the backend communicates with MySQL, S3/CloudFront and external APIs. The **LLM recommendation is split into a Python server** and connected via a Port/Adapter.

## Contribution 1 — Not feeding tens of thousands of places to the LLM: it recommends categories (cat3) only

<Callout kind="problem">

I wanted to recommend places with an LLM, but the simplest approach (sending user input + all place data straight to the LLM) would require feeding the **tens of thousands of places** from the Korea Tourism API as input tokens — impossible due to **context limits and cost**.

</Callout>

<Callout kind="goal">

Keep the LLM's natural-language recommendation ability, but build a structure that is **feasible at a realistic cost**.

</Callout>

<Callout kind="solution">

I split responsibilities between the LLM and Spring. The LLM recommends only a **category (`cat3`)**, and ranking of actual places happens inside Spring.

- Convert the LLM's category label into the Tour API's internal `cat3` code
- Filter actual places by `cat3`, then rank on the backend by combining **emotion features · popularity · distance scores**
- When the frontend sends back the initial `cat3` code as `cat3Filter`, **the LLM step is skipped and only ranking runs**

</Callout>

<Callout kind="result">

Emotion-based personalized recommendations became possible without feeding tens of thousands of places into the LLM.

**Limitation:** there is no fallback response when the LLM call fails, and a long timeout applies to every retry. The next step is to shorten the timeout and add a rule-based fallback so request threads aren't held up. Redis caching (same-input LLM output) and a VectorDB-based RAG approach are further improvements I'm considering.

</Callout>

## Contribution 2 — Splitting two pagination patterns

<Callout kind="problem">

The place list had two different usage patterns: **regular page browsing** and **mobile infinite scroll**. Using offset alone would degrade performance and cause duplicate/missing rows in infinite scroll as data grows.

</Callout>

<Callout kind="solution">

I split the strategy. **Regular lists use Offset Pagination**, while **infinite scroll uses Cursor Pagination with `createdtime` + `contentid` as a composite sort key**. The cursor is Base64-encoded, and I fetch `size + 1` rows to decide whether a next page exists.

</Callout>

<Callout kind="result">

Infinite scroll gets stable next-page fetching, and even with identical `createdtime` values, the `contentid` tiebreaker **fixes the order**, preventing duplicates/omissions.

</Callout>

## Contribution 3 (solo refactoring) — Finding the bottleneck with execution plans and restructuring place search

<Callout kind="problem">

Over roughly 49k places, a text search such as `q=카페` ("cafe") was implemented as four `LOWER(col) LIKE '%카페%'` conditions plus an `EXISTS` correlated subquery to match category names.

`EXPLAIN ANALYZE` showed the real bottleneck was not the list query but the **count query**: a full table scan with the subquery repeated about 49k times, taking **about 755ms**. Because of the leading wildcard and `LOWER()`, adding a B-Tree index could not fix the text-search path.

</Callout>

<Callout kind="solution">

I **denormalized** place name, category and category name into a `search_text` column and switched to `FULLTEXT INDEX … WITH PARSER ngram` + `MATCH … AGAINST`.

</Callout>

<Callout kind="result">

After the change, the list query finds candidates (about 3,468 rows) directly from the fulltext index, **about 4.9ms** end to end, and the count query no longer does a full scan or repeats the subquery.

Caveat: 755ms (count, before) and 4.9ms (list, after) measure different queries. Comparing only the old `LIMIT 20` list query in isolation can make the old approach look faster, so since the API runs both list and count, I judged by the whole search path rather than a single number. I documented the migration steps, SQL-log tests and before/after execution plans in [8 documents](https://github.com/sanghyunbang/Heat_Trip_Spring_Boot_BE/tree/main/docs/database/sql-query-optimization-search) (Korean).

**Limitation:** FULLTEXT results are not identical to `LIKE` (single-character and special-character queries). I treat this as a trade-off between performance and search semantics; finishing result comparisons for short queries and condition combinations is the next step.

</Callout>

## Contribution 4 (solo refactoring) — Building a quality & observability foundation

<Callout kind="problem">

External APIs, the LLM server, image uploads and auth were all failure-prone, and the recommendation/auth flows were core paths prone to regression on change. I needed **fast detection during development and a way to trace causes in production**.

</Callout>

<Callout kind="solution">

- **Unit tests** for recommendation orchestration, LLM-response DTO deserialization, and the auth service
- **JaCoCo** coverage reports (generated in the build) · **Qodana** static analysis (GitHub Actions)
- Collected controller latency & exceptions via **AOP**; errors are **deduplicated by fingerprint** then sent to **Slack**
- Sensitive-data masking + a `correlation id` for both log traceability and security

</Callout>

<Callout kind="result">

Core flows (recommendation · LLM DTO · auth) are guarded against regression by tests, and production errors can be noticed and traced faster via Slack alerts and `correlation id`. Qodana/JaCoCo are still at the visibility stage, but they're a starting point for tightening quality gates around core packages.

</Callout>
